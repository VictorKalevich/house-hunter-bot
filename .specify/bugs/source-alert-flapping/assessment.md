# Bug Assessment: пары сообщений «снова работает» / «отказал боту» при частичном пропуске сайта

- **Slug**: source-alert-flapping
- **Created**: 2026-11-23
- **Source**: pasted text (наблюдение на живом боте при выкате T088, таблица `sources` в D1)
- **Verdict**: valid
- **Severity**: medium

## Report (verbatim or summarized)

> Живой бот 2026-11-23: kufar.by пускает бота раз в час на один запрос, следующий через минуту — 403. В 13:17:48 UTC
> успешный запрос (29 новых объявлений) → источник ok, владельцу «kufar.by снова работает»; в 13:18:48 — 403 →
> blocked, владельцу «kufar.by отказал боту». После успеха backoff сбрасывается на 1 ч, поэтому пара сообщений
> приходит каждый час (~48 в сутки); то же у domovita при редких пропусках (Open Questions в
> .specify/bugs/domovita-423-blocked/assessment.md). US5-1: одно сообщение на сбой. Решение владельца: «снова
> работает» — только когда сайт ответит без отказа 3 запроса подряд (зеркально правилу «3 сбоя подряд»); пока сбой
> не закончен, новых «отказал боту»/«не отвечает» нет; проверки остаются раз в час (backoff после успеха
> по-прежнему сбрасывается), kufar продолжает отдавать свежие объявления.

Данные D1 после проверки в 13:17: kufar — `blocked`, `last_ok_at` 13:17:48, `alerted_at` 13:18:48, `backoff_level` 1,
следующая проверка 14:18:48; объявлений kufar 116 → 145. То же раньше у domovita: 11:44:48 «снова работает»,
11:47:48 снова «не отвечает».

## Symptom

Когда сайт пропускает один запрос из серии отказов, бот закрывает сбой на первом же успехе и отправляет «снова
работает», а на следующем отказе открывает новый сбой и шлёт новое сообщение о сбое. Ожидается (FR-020: не больше
одного сообщения о сбое, пока сбой длится; решение владельца): сбой закрывается только после 3 успешных запросов
подряд, до этого новых сообщений о сбое нет.

## Reproduction

1. Источник в сбое, владельцу сообщили (`alerted_at` не NULL; `blocked` или `failing` после 3 сбоев).
2. Плановая проверка получает 200 → `onSuccess`: `state = ok`, `failing_since = NULL`, `alerted_at = NULL`,
   владельцу «снова работает».
3. Следующий запрос (через минуту) получает 403/423 → `onFailure`: новый `failing_since`, `alerted_at` пуст →
   `isConfirmedFailure` → владельцу «отказал боту … следующая проверка через 1 ч».
4. Через час — снова п. 2–3: пара сообщений каждый час.

## Suspected Code Paths

- `src/jobs/poll-feeds.js:157` `onSuccess()` — один успех сразу закрывает сбой: сбрасывает `alerted_at` и
  `failing_since`, отправляет `recoveryText`.
- `src/jobs/poll-feeds.js:172` `onFailure()` — новое сообщение, если `alerted_at === null`; `failing_since` берёт
  `src.failing_since ?? now`.
- `migrations/0001_init.sql` `sources` — счётчика успешных запросов подряд нет (есть только `consecutive_failures`).
- `specs/001-house-listing-alerts/data-model.md` (переходы `sources`: «failing/blocked ──успешный опрос──▶ ok (+
  «снова работает»…)»), `contracts/telegram-bot.md` «Сообщения владельцу о сбоях», `quickstart.md` §4 (строка «после
  200 — «снова работает»») — описывают восстановление по одному успеху.
- `tests/e2e/source-health.e2e.mjs` — тесты «затем 200 → «снова работает»», «кнопка «Проверить сейчас»» и
  «423 Locked …» ждут восстановления после одного успешного запроса.

## Root Cause Hypothesis

Сбой считается законченным по первому успешному запросу, без порога. Порог стоит только на входе в сбой
(`FAILS_TO_ALERT = 3` для `http`) и отсутствует на выходе, поэтому сайт, который пропускает редкие запросы,
открывает и закрывает сбой на каждой проверке. В разработке этого не было видно: на стенде сайты либо работали, либо
отказывали подряд. Уверенность: high — последовательность полей в D1 и сообщения совпадают с кодом `onSuccess`/
`onFailure`.

## Proposed Remediation

**Preferred**: счётчик успешных запросов подряд и порог восстановления 3.

- Миграция `0003`: `sources.consecutive_ok INTEGER NOT NULL DEFAULT 0`. Применяется к удалённой базе до выката (новая
  колонка со значением по умолчанию совместима со старым кодом).
- `src/config.js`: `OKS_TO_RECOVER = 3`.
- `onFailure`: `consecutive_ok = 0`; остальное без изменений (`failing_since` сохраняет начало сбоя, сообщение —
  только при `alerted_at === null`).
- `onSuccess`: `state = ok`, `consecutive_failures = 0`, `backoff_level = 0`, `next_check_at = NULL` — как сейчас
  (сайт опрашивается дальше обычным порядком, проверки после отказа снова через 1 ч); `consecutive_ok + 1`.
  - Владельцу о сбое не сообщали (`alerted_at` NULL) — как сейчас: сбой закрыт, `failing_since`, `error_*` очищены.
  - Сообщали и успехов подряд стало 3 — «снова работает» с длительностью от исходного `failing_since`, `alerted_at`,
    `failing_since`, `error_*` очищены.
  - Сообщали, успехов меньше 3 — молча: `alerted_at` и `failing_since` остаются, следующий отказ не шлёт нового
    сообщения и продолжает тот же сбой.
- Документы: data-model.md (поле и переход «3 успешных опроса подряд»), contracts/telegram-bot.md (строка
  «Восстановление»), quickstart.md §4 (ожидание в таблице сквозного теста).

**Alternatives**:
- Без миграции — «2 успеха подряд» по `consecutive_failures = 0` перед успехом. Меньше правок, но порог не тот, что
  выбрал владелец.
- Не сбрасывать backoff после одного успеха (проверки 1→2→4→8→24 ч) — владелец этот вариант отклонил: kufar почти
  перестал бы давать объявления.

## Risks & Considerations

- «Снова работает» приходит на 2 минуты позже, чем раньше (3 запроса к сайту — 3 тика), — для настоящего
  восстановления это незаметно.
- Пока сбой не закрыт, другой вид сбоя того же сайта (например, robots.txt закрыл адрес) тоже не даст нового
  сообщения — так уже работает переход `failing` → `blocked`; «Источники» и баннеры в мини-приложении показывают
  текущее состояние независимо от сообщений.
- Миграция: порядок выката — сначала `npx wrangler d1 migrations apply house-hunter --remote`, потом
  `npx wrangler deploy`; иначе `UPDATE … consecutive_ok` в новом коде упадёт. Записей D1 — 4 строки.
- CPU и подзапросы не меняются: поле пишется в том же `UPDATE`.
