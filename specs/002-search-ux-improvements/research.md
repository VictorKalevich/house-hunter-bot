# Research: тип объекта, итог поиска и сайты в поиске

**Фича**: `002-search-ux-improvements` | **Дата**: 2026-11-22 | **План**: [plan.md](plan.md)

Опирается на исследование 001 ([research.md](../001-house-listing-alerts/research.md)): сайты, платформа и лимиты не
меняются. Документация — Context7: D1 (`/llmstxt/developers_cloudflare_d1_llms-full_txt` — `ALTER TABLE … ADD
COLUMN`, `wrangler d1 migrations apply`), мини-приложения Telegram (`/websites/core_telegram_bots_webapps` —
`showPopup`, `PopupButton`). Неясностей в Technical Context нет: всё ниже — выбор между вариантами.

## R1. Тип объекта у объявления

- **Decision**: колонка `listings.kind` — `house` | `cottage` | `dacha` | `part`, `NULL` — тип неизвестен (объявление
  записано до фичи). Адаптеры уже отдают `RawListing.kind` (contracts/source-adapter.md 001) и отбрасывают прочие
  типы; нормализация передаёт его в строку, вставка пишет. Для известного объявления `kind` обновляется в том же
  `UPDATE`, что цена и площади, если сайт показал другой тип или у строки его не было (`changedFields` в
  `src/jobs/ingest.js`). Индекса нет: тип проверяется среди строк, уже отобранных по широте и дате.
- **Rationale**: без новых запросов к сайтам (FR-020); тип нужен фильтру и уведомлению — Конституция разрешает
  хранить именно такое (принцип I). Дозаполнение старых строк — одна запись на объявление, и только когда бот снова
  его видит; если фича выкатывается вместе с 001, таких строк нет вовсе.
- **Alternatives**: выводить тип из адреса (у realt `sale-dachi`/`sale-cottages`) — только для одного сайта и без
  «части дома»; отдельная таблица типов — лишний JOIN ради четырёх значений; дозаполнять отдельным проходом по
  базе — лишние записи D1 без пользы для тех, кого бот уже не видит.

## R2. Выбор типов в поиске

- **Decision**: колонка `searches.kinds` — группы через запятую в постоянном порядке, как `searches.sources`:
  `house` («Дом или коттедж» = `house` + `cottage`), `dacha`, `part`; `DEFAULT 'house,dacha,part'`, `NOT NULL`.
  В API — `Criteria.kinds: string[]`, необязательный во входе (нет → все три), непустой. Объявление проходит, если
  `kind IS NULL` или группа его типа выбрана (FR-004). В списке условие добавляется в SQL, только когда выбраны не
  все группы, и повторяется в `passesFilters` — так же устроены сайты и диапазоны.
- **Rationale**: группы задал владелец; список через запятую уже используется для сайтов, проверка и разбор —
  те же. Старые клиенты и сквозные тесты без `kinds` получают «все типы».
- **Alternatives**: четыре отдельных типа в поиске (коттедж отдельно от дома — продавцы выбирают его как попало);
  битовая маска — нечитаемо в SQL и логах.

## R3. Населённый пункт без расстояния

- **Decision**: проверка условий (`validateCriteria`) отклоняет `settlementId` без `maxKm`:
  `fields.maxKm = «Укажите расстояние или очистите населённый пункт»`; та же проверка — в форме до отправки. Отбор
  поисков не меняется: сохранённые раньше поиски с пунктом без расстояния работают как прежде, пока их не изменят
  (FR-008).
- **Rationale**: ошибка — у поля, которое надо заполнить; правило в одном месте на сервере, форма лишь экономит
  запрос.
- **Alternatives**: подставлять расстояние по умолчанию (30 км) — незаметная подмена; молча снимать пункт — поиск
  перестаёт быть тем, что выбрал человек; переписать старые поиски миграцией — меняет чужие условия без их ведома.

## R4. Предупреждение о поиске без условий

- **Decision**: только в форме. Условий нет, если пусты расстояние и все шесть границ цены и площадей (типы и сайты
  не в счёт). Перед отправкой — `Telegram.WebApp.showPopup` (Bot API 6.2+): заголовок «Поиск без условий», текст
  ≤ 256 символов, кнопки `{ id: 'save', type: 'default', text: 'Сохранить так' }` и `{ type: 'cancel' }`; callback
  получает `id` нажатой. Вне Telegram или в старом клиенте — `window.confirm`. Сервер такой поиск принимает, как в
  001 (FR-006 001: любое условие можно не задавать).
- **Rationale**: владелец просил предупредить, а не запретить; `showPopup` даёт свои подписи кнопок (у `showConfirm`
  — только «OK»/«Отмена»).
- **Alternatives**: запрет на сервере — противоречит 001; подсчёт ожидаемого числа сообщений — нужен отдельный
  запрос и история хотя бы за сутки, которой в первые дни нет.

## R5. Итог поиска — экран поиска

- **Decision**: адрес `#/search/{id}` теперь — итог (раньше — форма). Форма изменения — `#/search/{id}/edit`, нового
  поиска — `#/search/new`, копии — `#/search/new?copy={id}`. После сохранения (нового или изменённого) —
  `#/search/{id}` и всплывающее «Поиск сохранён». Итог грузит параллельно `GET /api/searches/{id}`,
  `GET /api/searches/{id}/listings?page=1` (число N, флаги неточности) и `GET /api/sources` (строка о сайтах). На
  итоге: заголовок и метка «Активен»/«Пауза», условия строками, «Сейчас подходит N объявлений» + «Показать
  объявления», обещание уведомлений или «на паузе», переключатель паузы, «Изменить условия», «Копировать поиск»,
  «Удалить поиск». «Назад» Telegram: итог → «Мои поиски», форма изменения и копии → итог, новая форма → «Мои
  поиски», список → итог.
- **Rationale**: один экран и для «после сохранения», и для «открыть из списка» (FR-005) — меньше кода и одно место,
  где видно, что поиск делает. Кнопки меню бота (`/app#/search/new`, `/app#/`) не меняются. Число N — тот же запрос,
  что у первой страницы списка, поэтому оно совпадает со счётчиком списка; запрос заодно ставит маршруты списка в
  очередь, как раньше.
- **Alternatives**: отдельный экран «сохранено» плюс форма по нажатию в списке — два почти одинаковых экрана;
  сообщение в чат после сохранения — шум, итог и так перед глазами.

## R6. Копирование поиска

- **Decision**: без нового метода API. «Копировать поиск» открывает `#/search/new?copy={id}`: форма загружает поиск
  `{id}` и подставляет его условия, заголовок формы — «Копия: <название>». «Сохранить» — обычный `POST
  /api/searches`: новый поиск включён, `active_since` = сейчас (FR-016).
- **Rationale**: копия почти всегда отличается от исходного (сайты, расстояние) — правка перед сохранением
  естественна, а случайных одинаковых поисков не появится.
- **Alternatives**: `POST /api/searches/{id}/copy` — сразу второй такой же поиск, который всё равно надо менять.

## R7. Метки «Новое» и «обновлено» в списке

- **Decision**: в `ListingCard` добавляются `isNew` (`listings.is_new = 1` — то же правило «новое на сайте», что и
  для уведомлений) и `createdAt` (`site_created_at`: дают realt.by и domovita.by). Карточка: у нового — метка
  `ds-chip--brand` «Новое» и «размещено N назад»; у остальных — «обновлено N назад» (`publishedAt`: время
  размещения или поднятия по данным сайта) и, если есть `createdAt`, «· размещено 3 окт.». Объявления первого опроса
  сайта — не новые, как и для уведомлений (001).
- **Rationale**: слово «поднято» утверждало бы то, чего бот не знает (объявление могло просто лежать в выдаче);
  «обновлено» верно для обоих случаев, а метка «Новое» отвечает на главный вопрос. `ds-chip--brand` в дизайн-системе
  заведён именно для метки «Новое».
- **Alternatives**: отдельный признак «поднято» (сравнение `published_at` и `site_created_at`) — есть только у двух
  сайтов из четырёх.

## R8. Неточное число и маршруты «по дороге»

- **Decision**: ответ `GET /api/searches/{id}/listings` получает `totalApprox` — `true`, если запрос прочитал
  предельное число строк (`LIST_MAX_ROWS`), и тогда `total` — нижняя граница («не меньше N», в счётчике списка —
  «из N+»); и `distancesPending` — `true`, если у части подходящих объявлений дорожное расстояние ещё считается
  (их число может уменьшиться). Итог показывает подсказку «расстояния по дороге ещё считаются — число может
  уточниться в ближайшие минуты» (FR-007).
- **Rationale**: оба факта уже известны в `searchListings`; новых запросов нет.
- **Alternatives**: точный `COUNT(*)` отдельным запросом — расстояние до места проверяется только в коде, SQL не
  посчитает его точно.

## R9. Состояние сайтов для всех пользователей

- **Decision**: `GET /api/sources` для любого пользователя с доступом. По каждому из четырёх сайтов —
  `state`: `down` | `collecting` | `ok`, `since` и `checkedAt`:
  - `down` — сбой подтверждён тем же правилом, что сообщение владельцу: `blocked` или `disallowed`, либо `failing` и
    `consecutive_failures ≥ FAILS_TO_ALERT` (3). Правило выносится в одну функцию и используется и в
    `poll-feeds` (решение «сообщить владельцу»), и в API, чтобы они не разошлись (FR-018). Признак «сообщение
    отправлено» (`alerted_at`) не годится: сообщение могло не уйти. `since` — `failing_since`;
  - `collecting` — сбоя нет, но хотя бы у одной ленты адаптера нет строки `feeds` или её `last_ok_at` пуст
    (первый круг не закончен; до первого тика строк нет вовсе);
  - `ok` — остальное; `checkedAt` — `sources.last_ok_at`.
  Текст ошибки (`error_text`) пользователям не отдаётся. Строка на «Мои поиски»: всё работает — «Все сайты
  работают · проверены за последние N мин» (N — от самой давней из проверок); `down` — карточка «realt.by не работает
  с 14:05 — объявления с него придут, когда он заработает»; `collecting` — «Собираю объявления в первый раз:
  realt.by, domovita.by — это занимает до получаса». Итог поиска и список показывают только сайты этого поиска в
  состоянии `down`; пустой список при `collecting` среди сайтов поиска — FR-012.
- **Rationale**: два запроса к D1 одним `batch`, без записи; время «с 14:05» мини-приложение пишет по часам
  телефона, как остальные даты.
- **Alternatives**: показывать сбой с первой неудачной проверки — мигает при каждой случайной ошибке сети; отдавать
  состояние вместе со списком поисков — то же самое нужно ещё итогу и списку.

## R10. Подписи сайтов и описание поиска

- **Decision**: подписи охвата — в таблице сайтов мини-приложения рядом с названием (`src/app/app.js.txt`
  `SOURCES`): kufar.by — «вся страна»; realt.by — «вся страна»; domovita.by — «вся страна, без дач»; moyareklama.by —
  «Гомель и окрестности, цена только в рублях». Строка сайта в форме — `ds-list-item__body` с `__title` и `__meta`.
  Описание поиска в «Мои поиски» и условия на итоге перечисляют типы и сайты, только если выбраны не все.
- **Rationale**: охват — свойство адаптеров, которое меняется вместе с кодом мини-приложения; отдельный запрос ради
  четырёх постоянных строк не нужен.

## R11. Подпись способа и тип в тексте

- **Decision**: в названии поиска `road_center` → «по дороге от центра» (как в карточке и уведомлении; FR-010).
  Уже сохранённые названия пересобираются при следующем сохранении поиска. Тип в уведомлении — первым словом:
  «Дом», «Коттедж», «Дача», «Часть дома» и « · » перед ценой; неизвестен — строки типа нет (FR-002). В карточке тип —
  первая метка `ds-chip` в `ds-listing__top`, затем «Новое», затем сайт; сайт в `ds-listing__meta` больше не
  повторяется (FR-013).

## R12. Миграция и выкат

- **Decision**: `migrations/0002_kinds.sql` — два `ALTER TABLE … ADD COLUMN` (`listings.kind` с `CHECK` на четыре
  значения или `NULL`; `searches.kinds` с `NOT NULL DEFAULT`). Схема меняется без перезаписи строк, поэтому лимит
  записей D1 не страдает. Порядок выката: `wrangler d1 migrations apply house-hunter --remote` (миграция 0002) →
  `wrangler deploy`. Код 001 с применённой 0002 работает: новые колонки он не читает, а `searches.kinds` получает
  значение по умолчанию. Сквозной стенд применяет все файлы `migrations/*.sql` по порядку сам.
- **Rationale**: SQLite (а значит D1) добавляет колонку с постоянным значением по умолчанию без перестройки
  таблицы; `CHECK` проверяется на существующих строках — у них `NULL`, проверка проходит.
- **Alternatives**: пересоздание таблиц с новой схемой — запись каждой строки и окно, когда тик видит
  полуготовую базу.
