# Research: понравившиеся, «Не интересно» и изменение цены

**Фича**: `003-listing-likes` | **Дата**: 2026-11-23 | **План**: [plan.md](plan.md)

Опирается на исследования 001 и 002 ([001](../001-house-listing-alerts/research.md),
[002](../002-search-ux-improvements/research.md)): платформа, лимиты и адаптеры прежние. Документация:

- Context7, D1 (`/llmstxt/developers_cloudflare_d1_llms-full_txt`):
  - `batch()` — SQL-транзакция: если одна команда падает, откатывается вся пачка;
  - `rows_written` считает и записи в индексы.
- Context7, Telegram Bot API (`/websites/core_telegram_bots_api`) — только обзор раздела «Updating messages».
- Страница методов — официальная https://core.telegram.org/bots/api (Bot API 10.5, 2026-11-22), её в Context7 нет:
  - `editMessageReplyMarkup(chat_id, message_id, reply_markup)` возвращает изменённое сообщение. Срок 48 ч действует
    только для бизнес-сообщений не от бота; сообщения самого бота срока на правку не имеют.
  - `callback_data` — 1–64 байта.
  - `answerCallbackQuery.text` — до 200 символов; `show_alert` показывает окно вместо всплывающей строки.
  - `CallbackQuery.message` может оказаться `InaccessibleMessage` (`date = 0`) — такую кнопку не перерисовать.

Образцы страниц объявлений получены 2026-11-23 с адресов Cloudflare. Запросы шли временным Worker'ом
(`wrangler dev --remote`) с заголовками бота, не чаще раза в минуту к сайту:

| Сайт | Живое объявление | Снятое или несуществующее |
|---|---|---|
| realt.by | `/sale-cottages/object/3958190/` — 200, 280 КБ; `__NEXT_DATA__` ≈ 15 КБ: `pageProps.object` — `price`, `priceCurrency`, `priceRates`, `areaTotal`, `areaLand`, `status: 0`, `archive: 0` | старые номера — 404 |
| kufar.by | `re.kufar.by/vi/<id>` — 200, 1,2 МБ; цена и валюта — в `adView.data` на ~840 КБ от начала | 404 |
| moyareklama.by | `/single/ad/<id>` — 200, ≈ 34 КБ (`tests/fixtures/moyareklama/card.html`): `<div class="price">7 000 р.</div>`, площади в `<title>` | страница «Ошибка 404» |
| domovita.by | — | — |

domovita.by сейчас отвечает адресам Cloudflare `423` даже на `robots.txt`.

Неясностей в Technical Context нет. Ниже — выбор между вариантами.

## R1. Отметки пользователя

- **Decision**: таблица `marks`.
  - Состав: `user_id`, `listing_id`, `kind` (`like` | `hide`), `created_at`.
  - Ключ — `PRIMARY KEY (user_id, listing_id)`, `WITHOUT ROWID`.
  - `listing_id` → `listings (id) ON DELETE CASCADE`.
  - Индексы:
    - `marks_user (user_id, kind, created_at)` — экраны «Понравившиеся» и «Скрытые»;
    - `marks_kind (kind, listing_id)` — проверка страниц, очистка, сообщения о цене.
  - Одна строка на пару «пользователь + объявление». Поэтому лайк и «Не интересно» взаимоисключающие по устройству
    таблицы (FR-010): поставить одно — значит заменить `kind`, снять — удалить строку.
- **Rationale**:
  - Одна таблица — одно место правды о состоянии кнопки.
  - Ключ сам отвечает на вопрос «что у меня с этим объявлением» — так устроены карточки списка поиска.
  - Отметка относится к объявлению, а не к поиску (FR-002): удаление поиска её не трогает.
- **Alternatives**:
  - Две таблицы `likes` и `hidden` — взаимоисключение пришлось бы держать двумя командами и проверкой гонок.
  - Список id в `users` — не найти «у кого в понравившихся объявление X» без чтения всех пользователей.
  - Отметка на уровне `notifications` — у объявления из списка поиска уведомления может не быть.

## R2. Изменение отметки: одна команда, лимит 100, повторные нажатия

- **Decision**: действия — явные, а не «переключить»: «поставить лайк», «снять лайк», «скрыть», «вернуть».
  - Поставить: `INSERT … SELECT … WHERE (число лайков пользователя без этого объявления) < 100 ON CONFLICT
    (user_id, listing_id) DO UPDATE SET kind = 'like'`.
  - Время лайка обновляется, только если раньше отметка была другой: повторный лайк не поднимает дом в начало
    списка.
  - 0 изменённых строк означает отказ «В понравившихся уже 100 объявлений — уберите лишние» (FR-006).
  - Скрыть — тот же `ON CONFLICT … SET kind = 'hide'` без лимита.
  - Снять и вернуть — `DELETE … WHERE kind = <какой снимаем>`.
  - Объявления нет (удалено очисткой) — проверка до записи: «Объявление уже удалено из бота».
- **Rationale**:
  - Два быстрых нажатия одной кнопки до перерисовки дают одно и то же действие дважды. Итог совпадает с последним
    нажатием, лишних строк нет (край «два раза подряд»).
  - Кнопка-переключатель отменила бы первое нажатие вторым.
  - Лимит проверяется той же командой, что пишет: гонки двух вкладок не превышают его больше чем на единицу.
- **Alternatives**:
  - `callback_data` «переключить» — гонка двойного нажатия.
  - Отдельный `SELECT COUNT` перед `INSERT` — лишний подзапрос и окно гонки.
  - Без лимита — суточная проверка растёт без предела (принцип I).

## R3. Кнопки под сообщениями в чате

- **Decision**: у уведомления о новом объявлении и у сообщения об изменении цены — две строки кнопок:
  - первая: «Открыть объявление» (`url`);
  - вторая зависит от отметки:

    | Отметка | Кнопки второй строки | `callback_data` |
    |---|---|---|
    | нет | «♡ Нравится», «Не интересно» | `lk:<id>`, `hd:<id>` |
    | лайк | «♥ В понравившихся», «Не интересно» | `ul:<id>`, `hd:<id>` |
    | скрыто | «Скрыто · вернуть» | `uh:<id>` |

  - `<id>` — `listings.id`. Самый длинный вариант — 3 + 15 цифр, меньше 64 байт.
  - Отметка при отправке берётся из `marks`: пользователь мог поставить лайк в мини-приложении раньше, чем ушло
    сообщение.
- **Нажатие**:
  - проверка доступа — как у всех действий бота;
  - запись отметки (R2);
  - `answerCallbackQuery` с короткой строкой: «Добавлено в понравившиеся», «Убрано из понравившихся», «Скрыто —
    больше не покажу», «Возвращено»;
  - отказ по лимиту и «Объявление уже удалено из бота» — `show_alert: true`;
  - `editMessageReplyMarkup(chat_id, message_id, …)` с клавиатурой по новой отметке.
- **Правила кнопок**:
  - Кнопки отметок обрабатываются для любого пользователя с доступом, до проверки «только владелец», которая
    остаётся у `inv`, `users`, `rv`, `src`, `probe`.
  - Ответ «message is not modified» и недоступное сообщение (`date = 0`) — не ошибка: отметка уже записана, кнопки
    не перерисовываются.
  - Старые уведомления, отправленные до фичи, остаются с одной кнопкой: сообщения не правятся задним числом.
- **Rationale**:
  - Состояние видно на самой кнопке (FR-001).
  - Правка разметки — тем же сообщением, без новых сообщений в чате (Assumptions spec).
  - 4 подзапроса на нажатие: D1 чтение+запись одним `batch`, `answerCallbackQuery`, `editMessageReplyMarkup`.
- **Alternatives**:
  - Реакции Telegram (`message_reaction`) как лайк:
    - нужен `allowed_updates: message_reaction` и права;
    - на чужое сообщение в личке бот получает реакции не во всех клиентах одинаково;
    - не уместить «Не интересно» и «вернуть».
  - Новое сообщение-подтверждение на каждое нажатие — засоряет чат.

## R4. Скрытые: где их не показывать

- **Decision**:
  - **Список поиска и «Сейчас подходят»** (FR-009). `searchListings` присоединяет отметку пользователя: `LEFT JOIN
    marks m ON m.user_id = ? AND m.listing_id = l.id` (поиск по ключу) и отбрасывает `m.kind = 'hide'`. Отметка
    уходит в карточку (`mark`).
  - **Отправка**:
    - `deliverStep` присоединяет `marks` к уведомлению.
    - Скрытое → `failed` с `last_error = 'скрыто пользователем'`: статусы `notifications` прежние, `CHECK` без
      перестройки таблицы.
    - Для сообщений о цене — R10.
  - **Поднятое объявление**. Отбор (`matchStep`) не меняется: о поднятом сообщений нет и без фичи —
    `UNIQUE (user_id, source, external_id)` у `notifications`.
  - **Новое объявление**. Скрыть его можно только после того, как оно появилось в списке. Окно между записью
    уведомления и отправкой — один тик, поэтому проверки при отправке достаточно.
- **Rationale**:
  - Одно условие в SQL списка и одно при отправке закрывают все пути, которыми скрытое могло бы показаться
    (SC-006).
  - Отбор остаётся общим для всех пользователей.
- **Alternatives**:
  - Фильтр в `matchStep` — лишнее чтение `marks` на каждую пачку ради случая «скрыл за минуту до отправки», который
    отправка и так ловит.
  - Удалять уведомление при скрытии — теряется отметка «уже сообщали»; объявление, вернувшееся из скрытых, пришло
    бы второй раз.

## R5. Хранение понравившихся

- **Decision**: суточная очистка удаляет объявление, только если на него нет лайка:
  `DELETE FROM listings WHERE last_seen_at < ? AND NOT EXISTS (SELECT 1 FROM marks m WHERE m.kind = 'like' AND
  m.listing_id = listings.id)`.
  - Скрытые удаляются вместе с объявлением через `ON DELETE CASCADE` (Assumptions spec).
  - Сообщения о цене удаляются тем же каскадом, уведомления 001 — `SET NULL`, как раньше.
  - После снятия последнего лайка объявление снова подчиняется правилу 30 дней (FR-005).
- **Rationale**: одно условие в существующей команде; пометка «снято» и цены сохраняются в той же строке.
- **Alternatives**:
  - Копировать понравившиеся в отдельную таблицу — две копии одного объявления, двойная логика карточки.
  - Флаг `listings.liked` — его надо держать в согласии с `marks` при каждом нажатии.

## R6. Страница объявления: какие сайты и как понять «снято»

- **Decision**: адаптер может объявить
  `cardRequest(listing) → { url, accept }` и `parseCard(body) → { gone: true } | { gone: false, price,
  priceCurrency, houseArea, plotArea }`. Поля — в формате `RawListing`; контакты и текст не читаются.
  - **realt.by**:
    - адрес — `listings.url` (на сайте он зависит от области и раздела);
    - разбор — `__NEXT_DATA__` → `pageProps.object` теми же функциями, что выдача (`readPrice`, площади);
    - `archive` истинно → снято.
  - **moyareklama.by**:
    - адрес — тот же, что у карточки ради координат (`/single/ad/<id>`);
    - цена — `<div class="price">` (рубли);
    - площади — из `<title>` той же функцией, что выдача.
  - **Общее правило** (в `poll-feeds`, не в адаптере):
    - `404` и `410` → снято;
    - `403`, `423`, `429`, страница защиты → отказ защиты, как у ленты;
    - тайм-аут, `5xx`, неразобранная страница `200` → «не удалось».
  - **kufar.by и domovita.by** — без проверки страницы в этой фиче:
    - **kufar.by**:
      - страница объявления живёт на `re.kufar.by`, а бот читает выдачу и `robots.txt` с `api.kufar.by`.
        Проверка по правилам принципа I потребовала бы второго `robots.txt` на один сайт, а с ним — второго запроса
        в тот же круг;
      - страница весит 1,2 МБ;
      - kufar.by большую часть суток отказывает адресам Cloudflare (403).
    - **domovita.by** отказывает (423) даже на `robots.txt`, образца страницы нет.
    - Объявления этих сайтов обновляются по выдаче; если их нет в выдаче 7 дней — пометка «не удалось проверить»
      (R8).
- **Rationale**:
  - **Статус ответа — самый надёжный признак «снято»**: оба образца старых номеров — 404. У живого объявления
    realt `archive: 0`, поэтому истинное значение — снятое; это сверить на живом боте (quickstart.md §5).
  - Отказ защиты — не «снято» (FR-013) и, как у карточки ради координат, переводит источник в `blocked`: обход не
    делаем.
  - Перенаправление на другую страницу без объявления — «не удалось», а не «снято»: ложная пометка «снято» хуже
    отсутствия пометки.
- **Alternatives**:
  - Проверять kufar через `api.kufar.by` — открытого метода «одно объявление» в выдаче, которую читает бот, нет;
    адрес угадывать не будем.
  - Читать `robots.txt` каждого хоста отдельно — второе состояние `robots` на источник ради сайта, который сейчас
    почти всегда отказывает. Вернуться к этому, если kufar.by перестанет отказывать.
  - Признак «снято» по тексту страницы («объявление снято») — тексты меняются, статус надёжнее.

## R7. Когда проверять страницы

- **Decision**: проверка страницы — ещё один вид работы сайта в шаге тика «ленты», рядом с `robots`, `detail` и
  `feed`. Она идёт в том же слоте: один запрос к сайту за тик и пауза ≥ 1 минуты (`claimSite`).
  - **Кого проверять**: объявление с лайком хотя бы одного пользователя, если одновременно:
    - `checked_at` старше 24 ч или его нет;
    - бот не видел объявление в выдаче последние 24 ч (`last_seen_at`). Выдача уже подтвердила, что оно на месте, и
      дала цену; лишний запрос к сайту не нужен.
  - Один запрос на объявление, сколько бы лайков у него ни было (FR-012); самые давние проверки — первыми.
  - **Как часто**: колонка `sources.cards_next_at`.
    - Проверка страницы берёт слот сайта, только если `cards_next_at ≤ сейчас`.
    - После проверки `cards_next_at = сейчас + 3 мин`: страницы занимают не больше трети запросов к сайту, ленты не
      голодают; это до 480 страниц в сутки на сайт.
    - Если проверять некого — `сейчас + 1 ч`, поиск «кого проверять» не повторяется каждую минуту.
  - **Кто первым**: проверка страницы идёт впереди ленты, если подошло её время. Работа для координат
    (`needs_detail`) — впереди проверки страницы: новое объявление ждёт уведомления.
  - **Источник `blocked` или `disallowed`** — страниц не проверяем. Отказ защиты на странице объявления переводит
    источник в `blocked` (как карточка ради координат).
  - **Неудача** не повторяется раньше чем через сутки: `checked_at` пишется при любом исходе.
  - **`robots.txt`**: адрес образца страницы добавляется к адресам, которые бот сверяет с `robots.txt`
    (`urlsToCheck`). Закрыли страницы — источник `disallowed` по общему правилу.
- **Rationale**:
  - Принцип I держится тем же механизмом, что и для лент.
  - 100 лайков × единицы пользователей — сотни страниц в сутки на сайт: проверка укладывается в сутки (SC-004: ≤ 26
    ч) при доле слотов ≤ 1/3.
  - Без `cards_next_at` поиск «кого проверять» читал бы `marks` каждую минуту на каждом сайте.
- **Alternatives**:
  - Проверять все страницы в суточном cron — 50 подзапросов на вызов и 1 запрос в минуту к сайту: в один вызов
    влезает 1–3 страницы.
  - Отдельный cron раз в 10 минут — второй источник запросов к сайту в обход `claimSite`-порядка тика.
  - Проверять даже то, что было в выдаче за сутки, — двойная нагрузка на сайт без новой информации.

## R8. Пометки на карточке

- **Decision**: в `listings` три колонки:
  - `checked_at` — последняя попытка;
  - `check_ok_at` — страница последний раз подтвердила, что объявление на месте;
  - `gone_at` — проверка увидела «снято»; `NULL` — не снято.

  Состояние для карточки (`ListingCard.siteStatus`) считается при чтении:

  | Условие | `siteStatus` | Текст на карточке |
  |---|---|---|
  | `gone_at` не `NULL` | `{ kind: 'gone', at: gone_at }` | «Снято с сайта 24.11» |
  | иначе, если у объявления лайк этого пользователя и `MAX(last_seen_at, check_ok_at) < сейчас − 7 суток` | `{ kind: 'unchecked', lastSeenAt: last_seen_at }` | «Не удалось проверить; в выдаче сайта последний раз 12.11» |
  | иначе | `null` | — |

  - **Возврат на сайт**. Объявление снова в выдаче (`ingest`) или страница на месте (проверка) → `gone_at = NULL`
    (US3-3). `ingest` читает `gone_at` вместе с ценой и площадями.
  - **Повторная проверка**. Снятое тоже проверяется раз в сутки — так видно, что оно вернулось.
- **Rationale**:
  - Две даты вместо «состояния» отвечают на оба вопроса пометок (FR-014) без переходов, которые надо
    поддерживать.
  - «Не удалось проверить» только у своих понравившихся. Чужое объявление, которое бот не проверял, такой пометки
    не заслуживает. kufar.by и domovita.by без проверки страниц попадают сюда через 7 дней без выдачи — так
    честнее, чем «снято».
- **Alternatives**:
  - Колонка `check_state` (`ok` / `gone` / `failed`) — теряется дата последнего подтверждения.
  - Пометка «давно не встречалось» без проверки (как в запросе до уточнения) — через неделю она висела бы почти на
    всех понравившихся.

## R9. Цена продавца и что считать изменением

- **Decision**: в `listings` две колонки:
  - `price_amount` — цена в валюте продавца;
  - `price_currency` — `USD` | `BYN` | `EUR`, `NULL` — валюта неизвестна.

  Адаптер передаёт валюту продавца в `RawListing.priceCurrency`:

  | Сайт | Откуда валюта | Сумма | Нет валюты |
  |---|---|---|---|
  | realt.by | `priceCurrency` 840/933/978 | `price` | — |
  | kufar.by | `currency`: `BYR` → `BYN`, `USD`; `EUR` — валюта есть | `price_byn`/`price_usd`; у `EUR` суммы в евро в выдаче нет → `NULL` | — |
  | moyareklama.by | всегда `BYN` | цена в рублях | — |
  | domovita.by | — | — | `NULL` |

  Изменение — чистая функция `priceChange(old, next)` в `src/match/price-change.js`:
  1. **Валюта продавца известна и одна и та же** у старой и новой цены → сравниваются `price_amount`. Изменение — если
     разница ≥ 1 % старой цены (FR-016).
  2. **Иначе** — по `price_usd` и `price_byn`:
     - есть обе старые и обе новые → изменение, если обе сдвинулись в одну сторону, каждая ≥ 1 %;
     - есть одна общая → она сдвинулась ≥ 1 %.
  3. **Цена появилась или пропала** (`NULL` с одной стороны во всех парах) — не изменение (FR-018).
  4. **Продавец сменил валюту** (`USD` → `BYN`) — сравнение по правилу 2.

  В сообщении — цена в валюте сравнения: `$`, `BYN`, `€`. По правилу 2 — в долларах, если они есть.

  Где проверяется:
  - в `ingest` — для известного объявления, у которого поменялись цены (`changedFields`);
  - в проверке страницы — R7.

  Обновление цены и вставка сообщений о цене идут одним `batch` (R10).
- **Rationale**:
  - Сумма в валюте продавца не меняется от курса, поэтому ложных сообщений по курсу нет (SC-005, US4-2).
  - Правило 2 закрывает сайты без валюты продавца: при цене в долларах рубли меняются, доллары — нет, и наоборот.
  - Старые строки без `price_amount` получают его при первом же появлении в выдаче. Если цена при этом поменялась —
    сработает правило 2.
  - Порог 1 % отсекает округления сайтов при пересчёте.
- **Alternatives**:
  - Сравнивать только `price_usd` — ложные сообщения у цен в рублях при каждом движении курса.
  - Курс НБ РБ из `rates` для пересчёта — у сайтов свои курсы и округления, расхождение > 1 % бывает.
  - Хранить историю цен — не нужно ни одному сценарию.

## R10. Сообщения об изменении цены

- **Decision**: таблица `price_alerts`.
  - Поля: `user_id`, `listing_id` (→ `listings ON DELETE CASCADE`), `currency`, `old_price`, `new_price`, `status`,
    `attempts`, `next_attempt_at`, `last_error`, `created_at`, `sent_at`.
  - Статусы — как у `notifications` и ещё `cancelled`. Индексы — `(status, next_attempt_at)` и `(created_at)`.
  - **Вставка**: `INSERT INTO price_alerts (…) SELECT m.user_id, ?, … FROM marks m WHERE m.kind = 'like' AND
    m.listing_id = ?` в том же `batch`, что `UPDATE listings` новой цены.
  - `batch` — транзакция: либо записаны обе, либо ни одна.
  - Повтор обработки той же выдачи видит уже новую цену и сообщения не создаёт: «одно на изменение и пользователя»
    (FR-017) без отдельного ключа уникальности.
  - **Отправка** — в шаге `deliver` после уведомлений, из той же доли подзапросов:
    - тот же захват `pending → sending`, те же повторы 1, 5, 15, 60 мин, 403 → `undeliverable`, 429 → пауза
      (contracts/telegram-bot.md 001);
    - при отправке присоединяется отметка: лайка больше нет или объявление скрыто → `cancelled` без отправки
      (FR-017, край «лайк снят, а сообщение в очереди»);
    - пользователь без доступа → `undeliverable`, как у уведомлений.
  - **Текст** — contracts/telegram-bot.md 003: первая строка «Цена изменилась: было X, стало Y (±разница)», дальше
    строки уведомления о доме:
    - без строки расстояния и без строки поисков: лайк не привязан к поиску;
    - последняя строка — «realt.by · в понравившихся»;
    - кнопки — R3.
  - **Очистка** — как у уведомлений: старше года.
- **Rationale**:
  - Очередь и правила отправки — те же, что у проверенных в 001 уведомлений.
  - Отдельная таблица не трогает `UNIQUE (user_id, source, external_id)` у `notifications`: о том же объявлении
    может быть и уведомление, и сколько угодно сообщений о цене.
- **Alternatives**:
  - Колонка «вид» в `notifications` — `UNIQUE` и `CHECK` меняются только перестройкой таблицы со всеми строками
    (записи D1).
  - Отправлять сразу из `ingest` — вне доли подзапросов отправки и без повторов.
  - Склеивать два изменения подряд в одно сообщение — отправка идёт каждый тик, два изменения цены одного дома в
    одну минуту на практике не встречаются.

## R11. Экраны «Понравившиеся» и «Скрытые»

- **Decision**:
  - **API**: `GET /api/marks?kind=like|hide&page=N` — `{ items: ListingCard[], page, pageSize, total }`.
    - Порядок — по `marks.created_at` убыв.
    - Одним `batch`:
      - страница отметок с объявлениями (`marks_user`);
      - число отметок;
      - пункт самого нового поиска пользователя, у которого он задан.
  - **Расстояние** (FR-003) — по прямой от этого пункта: `ListingCard.distance` с полем `from` (название пункта).
    - Нет поиска с пунктом или у объявления нет координат → `distance: null`.
    - Дорожных расстояний здесь нет: лайк не привязан к поиску, а маршрут ради экрана лайков — лишний запрос к
      сервису.
  - **Отметки**: `PUT /api/listings/{id}/mark` с `{ "mark": "like" | "hide" | null }` (R2). Ответ — `{ id, mark }`.
    Ошибки:
    - `404` — объявления нет;
    - `409 like_limit` — лимит 100.
  - **Карточки** в списках поиска, «Понравившихся» и «Скрытых» получают `id`, `mark` и `siteStatus`.
- **Rationale**: один метод чтения на два экрана; `PUT` с итоговым состоянием идемпотентен, как кнопки в чате (R2).
- **Alternatives**:
  - `POST/DELETE /api/likes/{id}` и отдельные пути для скрытых — вдвое больше путей ради того же действия.
  - Расстояние от каждого поиска пользователя — несколько строк на карточке; какое из них главное, непонятно.

## R12. Мини-приложение

- **Decision**: без новых компонентов дизайн-системы.
  - **Кнопки на карточке** — строка `ds-row ds-row--wrap`:
    - отметка: «♡ Нравится» — `ds-btn ds-btn--sm ds-btn--secondary`; «♥ В понравившихся» — `ds-btn ds-btn--sm`,
      акцентная;
    - «Не интересно» — `ds-btn--secondary`;
    - «Открыть объявление»;
    - `aria-pressed` у кнопки отметки.
  - **Пометки**:
    - «Снято с сайта 24.11» — `ds-chip ds-chip--warning` среди меток карточки;
    - «Не удалось проверить; …» — строка `ds-hint` под местом.
  - **«Не интересно» в списке поиска** — карточка сменяется `ds-card` с `ds-row ds-row--between`: «Скрыто» и кнопка
    «Вернуть» (US2-1). В «Скрытых» на месте этой строки — «Вернуть».
  - **Экраны**: `#/liked?page=N` и `#/hidden?page=N`.
    - Тот же пейджер `ds-pager` и пустое состояние `ds-empty`: «Понравившихся пока нет — отмечайте дома ♡ в
      уведомлениях и списках».
    - На главном экране — кнопка «♥ Понравившиеся» (`ds-btn--secondary ds-btn--block`) под «Новый поиск».
    - На «Понравившихся» — ссылка «Скрытые» (`ds-btn--sm ds-btn--secondary`).
  - **Кнопка в меню бота**: «Понравившиеся» (`web_app` → `/app#/liked`) для всех пользователей (FR-004).
- **Rationale**:
  - Текст кнопки совпадает с кнопкой в чате (FR-001), состояние видно без иконки.
  - Нужные элементы уже есть в `design-system/` (принцип VII).
- **Alternatives**:
  - Сердечко-иконка `ds-icon-btn` в углу фото — нужен новый вариант компонента и подпись для чтения с экрана; ради
    одного символа не стоит.
  - Вкладки «Понравившиеся | Скрытые» на одном экране — компонента вкладок нет, а «Скрытые» нужны редко.

## R13. Поправка к конституции

- **Decision**: 1.2.0 → 1.3.0 (MINOR: расширение правил, ничего не снимается).
  - **Принцип I**, новый пункт: «Кроме выдачи, бот раз в сутки открывает страницу объявления, которое у
    пользователя в понравившихся, — чтобы узнать, снято ли оно и какая у него цена. Один запрос на объявление в
    сутки, и только если за сутки его не было в выдаче; запросы идут в общем порядке запросов к сайту (пауза ≥ 1
    мин); robots.txt и отказ защиты — по тем же правилам.»
  - **Принцип I**, пункт «Хранится только…» — плюс цена в валюте продавца и даты проверки страницы.
  - **«Безопасность и данные»**, пункт о пользователе — плюс «его отметки объявлений („нравится“, „не интересно“)».
- **Rationale**: spec прямо предусматривает поправку (FR-012, Assumptions). Принцип I запрещает читать что-либо
  кроме первых страниц выдачи — без поправки US3 нарушал бы конституцию.
- **Alternatives**: записать нарушение в Complexity Tracking без поправки — постоянное поведение бота должно быть в
  конституции, а не в исключении одного плана.

## R14. Нагрузка и лимиты

- **Decision** — оценки:
  - **Подзапросы**:
    - проверка страницы — 3 на тик: чтение «кого проверять», запрос к сайту, запись в общем `batch` шага;
    - нажатие в чате — 4;
    - `GET /api/marks` — 1 `batch`;
    - сообщения о цене — из доли отправки (≤ 20 за тик вместе с уведомлениями).
  - **CPU** — `cost` в `bench`:
    - страница realt — 2 (поиск `__NEXT_DATA__` в 280 КБ + разбор 15 КБ JSON);
    - страница moyareklama — 1;
    - тик со страницей берёт её вместо ленты, поэтому дороже не становится.
  - **Записи D1**:
    - отметка — 3 строки (таблица + 2 индекса);
    - проверка страницы — 1–2 (объявление, источник);
    - `cards_next_at` — 1 на проверку и ≤ 24 в сутки на сайт без работы;
    - всего ≲ 2 тыс. в сутки при сотнях понравившихся — на фоне ≈ 35 тыс. (quickstart 001 §7).
  - **Чтения D1**:
    - список поиска — плюс поиск по ключу `marks` на строку (≤ 3000);
    - «кого проверять» — индекс `marks_kind` по лайкам (сотни строк) не чаще раза в 3 минуты на сайт;
    - в пределах 5 млн в сутки с большим запасом.
- **Rationale**: принцип IV — меряется в `npm run bench` и сквозном тесте «сутки тиков» (quickstart.md).
